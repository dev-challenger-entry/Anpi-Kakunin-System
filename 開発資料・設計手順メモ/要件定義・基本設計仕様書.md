# 安否確認システム 要件定義・基本設計仕様書

> 本書は「要件定義／基本設計 仕様書叩き台メモ」を、実装済みのソースコード（Java / JSX）の内容に合わせて書き直したものです。
> 叩き台メモに記載があったが未実装の項目（ユーザー自己登録、JWT認証、論理削除、連絡手段の希望、enum型ステータス、イベント区切り機能など）は、末尾「9. 将来拡張として検討していた項目（未実装）」にまとめて残しています。

## 1. アプリケーション形式

本システムはSPA（Single Page Application）構成のWebアプリケーションである。

- フロントエンド：React（Vite）
- バックエンド：Spring Boot（REST API）
- データベース：MySQL
- フロントエンドとバックエンドはJSON形式でHTTP通信を行う（`fetch` + `credentials: 'include'`）
- 開発環境では `FrontendDevRunner`（`@Profile("dev")`）がバックエンド起動時に `npm run dev` を自動起動し、フロント・バック同時起動を実現している
- `.env` ファイルは `StudySpringApplication` の起動前処理でシステムプロパティとして読み込まれる（`ADMIN_PASSWORD` 等の機密情報を格納）

---

## 2. 対象ユーザーと運用モデル

- 想定利用者数：100名規模の企業を想定
- 会社員のみを対象とし、家族等の第三者は対象外
- **社員アカウントは管理者が「社員情報登録・変更画面」から直接登録する方式**とする
  （社員本人による自己登録は行わない）
- 管理者が社員ID・氏名・部署名・初期パスワードを入力して登録し、対象の社員はそのID/パスワードでログインする

---

## 3. 権限・ロール

`employees` テーブルの `role` カラム（`NOT NULL`）で管理する。値は以下の2種類のみを許可する。

| ロール値 | 意味 | 主な機能 |
|---|---|---|
| `ADMIN` | 管理者 | 集計結果の閲覧、社員情報の登録・変更・削除、自分自身の管理者情報の変更 |
| `USER` | 一般社員 | 自身の安否ステータスの報告・更新 |

- ロールの判定は `SessionAuthInterceptor` がセッションから取得した `role` を用いて行う
- `/api/admin/**` へのアクセスは `role = ADMIN` でなければ 403 を返す

---

## 4. データモデル

本システムは単一テーブル（`employees`）構成で稼働する（社員・管理者を1テーブルで管理し、`role` カラムで区別する）。

| カラム名 | 型 | 制約 |
|---|---|---|
| employee_id | varchar | PRIMARY KEY / NOT NULL |
| name | varchar | 制約なし |
| section_name | varchar | 制約なし |
| safety_status | varchar | 値はUSERのみ使用（日本語文字列。詳細は6章） |
| password_hash | varchar | 制約なし（BCryptハッシュを格納） |
| role | varchar | NOT NULL（"ADMIN" または "USER" のみ許可） |
| answered_time | datetime | 制約なし（安否状況の最終回答日時） |
| email | varchar | NULL許可（role=ADMINの場合のみ使用。USERの場合は常にNULL） |
| email2 | varchar | NULL許可（role=ADMINの場合のみ使用。USERの場合は常にNULL） |

- 初回起動時のサンプルデータ・管理者アカウント（`ADMIN001`）は `data.sql` に `INSERT IGNORE` で投入する
  （`DELETE FROM` → `INSERT INTO` 方式は起動のたびにデータをリセットしてしまうため採用しない）
- 初期パスワードは `SetupDefaultPasswords`（`@Profile("dev")`）が、`password_hash` が未設定のアカウントに対してのみ設定する（既にパスワードが変更済みのアカウントは上書きしない）
- 万一パスワードを忘れて管理者としてログインできなくなった場合に備え、`--spring.profiles.active=reset-password` 指定時のみ動作する強制リセット処理（`forceResetAdminPassword`）を用意している

### 最初の管理者アカウントについて

管理者は「社員情報登録・変更画面」からは登録できない（同画面はUSERロールの登録専用）。
そのため、最初の管理者アカウント（`ADMIN001`）は `data.sql` にあらかじめ記載しておくことで用意する。

## 5. 社員情報の登録・変更・削除

### 5.1 登録

- 「社員情報登録・変更画面」（`EmployeeManage.jsx`）から、社員IDで検索 → 該当社員が存在しなければ「新規登録に進みますか？」の確認を挟んで新規登録フォームへ遷移する
- この画面経由の登録は**常に一般社員（`USER`）として登録**する。管理者アカウントの新規作成はこの画面の対象外
- 必須項目：社員ID・社員名・部署名・新しいパスワード（確認用と一致していること）
- 登録時、安否ステータスの初期値は `"未回答"` で登録される

### 5.2 変更

- 検索でヒットした社員（`role = USER` のみ対象。`role = ADMIN` は編集対象外として弾く）について、氏名・部署名・パスワードを変更できる
- 本人確認は以下の2通りのいずれかで行う
  1. 対象社員自身の現在のパスワード（`currentPassword`）で照合
  2. 対象社員のパスワードが分からない場合、代わりにログイン中の管理者自身のパスワード（`adminPassword`）で照合
- どちらも未入力の場合は更新を拒否する

### 5.3 削除

- 「削除する」ボタン押下 → ブラウザ標準の確認ダイアログ → `DELETE /api/admin/employees/{employeeId}` を呼び出す
- **削除方式は物理削除**とする（`EmployeeRepository.deleteById`）。論理削除フラグ等は持たない
- `role = ADMIN` のアカウントは削除できない
- 削除成功後、画面の検索欄・入力欄をすべて初期状態に戻す

## 6. 安否ステータス

安否ステータスの値は、**enum型ではなく日本語文字列**として、DB・バックエンド・フロントエンドを通じて一貫して使用する。

| 値（DB・API共通） |
|---|
| `未回答` |
| `無事です` |
| `避難しました` |
| `出勤困難` |

- 社員が安否状況を更新すると、`safety_status` と `answered_time`（回答日時）が同時に更新される（`StatusController`）
- DB上で `safety_status` が `NULL` の社員（未回答）は、マイページ取得時に `"未回答"` として補完して返す（`EmployeeStatusDto`）

---

## 7. 集計機能

- 集計ロジックはすべてバックエンド（`AdminController#getStatusSummary`）が担う
- フロントエンド（`Admin.jsx`）は、バックエンドが集計済みの結果（ステータスごとの人数・回答者一覧）を受け取り、表として表示するだけとする。集計ロジックはフロントに持たせない
- 集計結果には管理者（`role = ADMIN`）は含めず、一般社員（`role = USER`）のみを対象とする
- 表示内容：ステータスごとの人数、回答者名、回答日時（`YYYY/MM/DD HH:mm` 形式）

## 8. セキュリティ要件

### 8.1 認証（誰なのかを確認する）

- **JWTではなく、`HttpSession` を用いたセッション認証**を採用する
    今の設計では、複数のサービスにまたがって認証情報を維持する必要がないから。
- ログインAPI（`POST /api/login`）成功時、セッションに `employeeId` と `role` を保存する
- 以降のリクエストは Cookie（セッションID）を用いて認証状態を維持する（フロント側は `credentials: 'include'` を指定）
- ログアウトAPI（`POST /api/logout`）はセッションを `invalidate()` して破棄する

### 8.2 パスワードのハッシュ化

- `spring-security-crypto` の `BCryptPasswordEncoder` を利用する（Spring Securityのフル機能・フィルタチェーンは使用しない）
- パスワードは平文でDBに保存せず、ハッシュ化した文字列のみを保存する
- ログイン時は入力されたパスワードをハッシュ化した結果と、DB上のハッシュを比較する

### 8.3 認可（ログイン済みでも、その操作をしてよいかを確認する）

- **`@PreAuthorize` は使用せず、`SessionAuthInterceptor`（`HandlerInterceptor`）による集中管理方式**を採用する
  （各コントローラーに認可ロジックを分散させない設計方針）
- `WebConfig` にて、以下のパスパターンに対してインターセプターを適用する
  - `/api/mypage`
  - `/api/status/**`
  - `/api/admin/**`
  - `/api/captcha/**`
  - （`/api/login` のみ除外）
- チェック内容
  1. 未ログインチェック：セッションに `employeeId` が無ければ401
  2. 管理者専用APIチェック：`/api/admin/**` へのアクセスで `role != ADMIN` なら403
  3. **本人確認チェック（IDOR対策）**：URLパス変数 `userId` を含むエンドポイント（例：`/api/status/{userId}`）では、ログイン中の `employeeId` とパス変数の `userId` が一致しない場合403を返す
- CORSのPreflightリクエスト（`OPTIONS`メソッド）は認証チェックを通過させる

### 8.4 CAPTCHA（画像認証）

- 管理者としてログイン成功後、集計画面（管理者画面）に到達する前に、CAPTCHA確認画面を挟む
- `CaptchaController` が4文字のランダム文字列（紛らわしい文字 `0/O`, `1/I` 等は除外）を生成し、正解はセッションにのみ保持する
- 将来的にGoogle reCAPTCHA等へ置き換える前提の、暫定的な文字列認証として現在、簡易実装している

### 8.5 通信

| 環境 | 対応 |
|---|---|
| 開発中 | `http://localhost:5173`（フロント）⇔ `http://localhost:8080`（バック）で、CORS許可を明示設定（`CorsConfig`）。暗号化なし |
| 本番公開時 | `CorsConfig` の `allowedOrigins` に本番URLを追加する必要あり（現状はコード内コメントで注意喚起のみ）。HTTPS化は今後の課題 |

- `CorsConfig` では `allowCredentials(true)` を指定し、Cookie（セッション）を用いたクロスオリジン通信を許可している

### 8.6 入力検証

- **`@Valid` によるアノテーションベースの自動検証は現状未導入**。各DTOにはBean Validationアノテーションを付与していない
- 入力チェックはフロントエンド（例：メールアドレスの `@` 個数チェック、パスワード確認一致チェック）およびバックエンドのService層（例：本人確認、二重登録防止、対象がADMINでないかのチェック）で個別に実装している

### 8.7 機密情報管理

- DBパスワードや初期管理者パスワード（`ADMIN_PASSWORD`）等は `.env` ファイルに記載し、`StudySpringApplication` 起動時にシステムプロパティとして読み込む方式とする
- ソースコード中に機密情報を直接記述しない
- ログ出力（`LocalUrlLogger` 等）にパスワードやセッション情報を出力しないよう留意する

## 9. 画面要件

| 画面 | 対象者 | URL（想定） | 主な機能 |
|---|---|---|---|
| ログイン画面 | 全員 | `/login` | 社員ID＋パスワードでログイン。失敗時は画面が真っ白になり赤字でエラー表示 |
| 確認画面（CAPTCHA） | 管理者のみ | `/admin/verify` | ログイン直後の管理者に対してのみ表示。文字列入力で認証 |
| マイページ画面 | 一般社員 | `/mypage` | 安否ステータス（未回答／無事です／避難しました／出勤困難）の選択・送信 |
| 送信完了画面 | 一般社員 | `/mypage`（同一URL内でstate切替） | 送信した安否ステータスと最終送信日時を表示 |
| 管理者画面（集計結果） | 管理者 | `/admin` | ステータス別人数・回答者一覧の表示、各種変更画面への遷移、ログアウト |
| 社員情報登録・変更画面 | 管理者 | `/admin/employees` | 社員IDで検索し、登録済みなら変更・削除、未登録なら新規登録 |
| 管理者情報変更画面 | 管理者 | `/admin/settings` | 自分の管理者名・メールアドレス・パスワードの変更 |

- 全画面共通：ログイン後30分操作がない場合、セッション切れとして再ログインを促す（フロント側は401応答を受けて画面をリロードする設計）
- ログアウト時は、ログイン画面を除き、画面が真っ白になり左上に赤字で「ログアウトしました。」と表示される

## 10. 将来拡張として検討していた項目（未実装）

以下は叩き台メモに記載されていたが、現状のコードには反映されていないアイデアである。今後の拡張候補として記録に残す。

- **社員本人によるアカウント自己登録**（社員番号マスタとの突合方式）。現状は管理者による代理登録のみ
- **JWTベースの認証**への移行（現状はセッション認証）
- **連絡手段の希望**（電話対応可 / 電話NG・メール希望）の管理。安否ステータスとは独立した項目として追加する案
- **安否ステータスのenum型管理**（現状はDB・API全体で日本語文字列を直接使用する方針を採用済みのため、型安全性より運用のわかりやすさを優先した形）
- **論理削除（`is_active`フラグ）＋一定期間後の物理削除運用**（現状は即時物理削除）
- **1年未アクセスの自動削除バッチ＋事前メール通知**（`last_login_at` カラム、`@Scheduled` による日次バッチ）
- **管理者による「新しい安否確認を開始／終了」の手動トリガー機能**（イベント区切りの概念）。現状は常時ステータスを保持・上書きする方式
- **`@Valid` によるアノテーションベースの入力検証の導入**
- **本番環境でのHTTPS化**
