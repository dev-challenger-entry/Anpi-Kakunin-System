

「要件定義」と「基本設計」仕様書叩き台メモ

**アプリケーション形式**
本システムはSPA（Single Page Application）構成のWebアプリケーションです。
フロントエンド（React）とバックエンド（Spring Boot）を分離し、
APIを介してJSON形式でデータをやり取りします。

**想定する対象ユーザー**
-想定利用者数：100名規模の企業を想定
-会社員のみ（家族は対象外）
-個人が各々でユーザー登録することを想定する

**閲覧権限**
-ADMIN: 管理者。部署ごとの安否状況を一覧・集計できる
-EMPLOYEE: 一般社員。自身の安否ステータスを報告する

**イベント区切り**
　本アプリは管理者権限を持つ人が手動トリガーで起動するものとする。
　管理者が「新しい安否確認を開始」ボタンを押し、終了を押すまでが１連のイベントとなる。
　
**ユーザー登録の方法**
　なりすまし登録・誤入力を防ぐため、自由入力ではなく社員番号マスタとの突合方式とする。
　事前に data.sql または管理者インポートにより「社員番号マスタ」（社員番号・氏名・部署）をDBに登録しておく。
　ユーザー登録画面に社員番号入力欄を設け、登録時にマスタと突合。一致しない場合は登録エラー
　一致した場合、氏名・部署はマスタ側の値を自動反映し、本人による自由入力は不可とする
　1つの社員番号につき1アカウントのみ登録可（重複登録はエラー）

**ユーザーデータ削除の運用ルール**
１．管理画面に「社員削除」機能を追加（ADMIN権限のみ、@PreAuthorize でロールチェック）
２．誤削除リスクを考慮し、まずは論理削除（is\_active フラグによる非表示化）とし、一定期間後に物理削除する運用とする
３．退職者の削除し忘れを防ぐため、1年未アクセスの自動削除：ユーザーテーブルに last\_login\_at（最終ログイン日時）を追加し、 Spring の @Scheduled による日次バッチで1年経過ユーザーを検出する。また、その１か月前に登録メールアドレスで通知をする。

**安否ステータス**
-UNANSWERED（未回答）
-SAFE（無事です）
-EVACUATED（避難しました）
-UNABLE\_TO\_COMMUTE（出勤困難）

**連絡手段の希望**
安否ステータスとは別に、社員ごとに希望する連絡手段を管理する。
災害時は電話が一斉に集中しやすく、本人の負担になる場合があるため、
安否状態とは独立して「電話対応可否」を選べるようにする。
-PHONE\_OK（電話対応可）
-EMAIL\_ONLY（電話NG・メール希望）

例：「避難しました」＋「電話NG・メール希望」、
　　「出勤困難」＋「電話対応可」のように、
　　安否状態と連絡手段の希望を自由に組み合わせ可。

**集計機能について**
　バックエンドで一元管理する。
　フロント（React）は「バックエンドが集計済みの結果」を受け取って、それを表やグラフとして表示するだけにするのがきれいな役割分担。集計ロジックそのものはフロントに持たせない、という設計方針。

**セキュリティ要件**

1\. 認証(にんしょう)「誰なのかを確認する」

Spring Security + JWT

* ログイン時にID・パスワードをチェックし、正しければ **JWT(JSON Web Token)** という認証済みの証明書のようなものを発行
* 以降のリクエストでは、このJWTを一緒に送ることで「ログイン済みユーザーだ」と証明できる(毎回パスワードを送らなくて済む)

BCryptでパスワードハッシュ化

* パスワードをそのままDBに保存すると、DBが漏れた時に全ユーザーのパスワードが流出する
* BCryptは「元に戻せない暗号化(ハッシュ化)」を行うアルゴリズムで、DBには変換後の文字列だけを保存
* ログイン時は「入力されたパスワードをハッシュ化した結果」と「DBに保存されているハッシュ」を比較する

\---

2\. 認可(にんか)「ログイン済みでも、その操作をしていいかを確認する」

@PreAuthorizeでロール制御

* ユーザーには「一般ユーザー」「管理者」のような役割(ロール)があり、メソッドの前に

java
  @PreAuthorize("hasRole('ADMIN')")


のように書くことで、そのロールを持つ人しか実行できないようにする

**自分のデータのみ操作可(本人確認チェック)**

* ロールが同じ「一般ユーザー」でも、Aさんのリクエストで**Bさんの**安否ステータスを書き換えられては困る
* そこで、リクエストに含まれる **「JWTから取れる本人のユーザーID」** と、**「更新しようとしている対象のユーザーID(URLやパラメータで指定されたID)」** を突き合わせて、一致しなければ拒否するチェックをコード内に入れる

java
  if (!loginUserId.equals(targetUserId)) {
      // 403エラーを返す
  }


\---

3\. 通信

|環境|対応|
|-|-|
|開発中|暗号化なしでひとまず問題なし|
|本番公開時|**CORS制限**(許可していない外部サイトからのアクセスをブロック)<br>**HTTPS必須**(パスワードやJWTなどの通信内容を暗号化し、盗聴を防ぐ)|

\---

4\. 入力検証

@Valid

* リクエストで送られてきたデータ(名前が空じゃないか、文字数は適切かなど)を、コントローラーに届く前に自動でチェックする

enum型でステータス制御

* 「安否ステータス」を自由な文字列(String)で受け取ると、タイプミスや不正な値が入る可能性がある
* 「無事」「要救助」「連絡待ち」のように、あらかじめ決まった選択肢だけを許可するenum型で定義すると、それ以外の値は受け付けなくなる

\---

5\. 機密情報管理

環境変数化

* DBのパスワードやJWTの署名に使う秘密鍵をソースコードに直接書くと、GitHub公開時に流出する
* `.env`ファイルやOSの環境変数に値を置き、コードからは「環境変数を読み込む」形にすることで、コード自体には機密情報が現れないようにする

ログ出力に注意

* デバッグ用にログを出す際、うっかりパスワードやJWTそのものを出力してしまうミスがよくある

ログファイルは意外と多くの人がアクセスできる場所に残るので、機密情報は絶対に出力しないよう気をつける
**画面要件**



|画面|対象者|主な機能|
|-|-|-|
|ログイン画面|全員|メール＋パスワードでログイン、JWT発行|
|ユーザー登録画面|全員|氏名・部署・メール・パスワード登録（個人が各自登録する想定）|
|安否報告画面|全員|安否ステータス（未回答/無事/避難/出勤困難）と連絡手段の希望（電話対応可/メール希望）を選択・更新|
|管理画面|管理職|部署ごとの安否状況一覧・集計結果（表またはグラフ表示|



※管理者は事前リスト登録方式で決めるが、それでも最初の１人はどうやって決めるのかという問題が残るため、
それはプログラム設計者がアプリ運用前にdata.sqlというファイルの中へ最初のひとりを記載しておくことで解決する。
